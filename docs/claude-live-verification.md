## The investigation

Question: *"Why are checkout requests failing with 503s? What changed, and what should we do?"* on incident INC-10.

| Measure | Value |
|---|---|
| Engine recorded | `analysisMode: llm`, provider `anthropic`, model `claude-haiku-5-5` (as reported by the API in its responses) |
| Model calls | 5 (plan, three tool rounds, report) |
| Tokens | 17,673 input · 14,678 output · 32,077 read from cache · 28,477 written to cache |
| Model time | 63.7 s |
| Estimated cost | $0.012987 (2.6% of the $0.50 per-investigation limit; 23% of the token limit) |
| Tool calls | 15: 2 by OpsPilot to load context, 13 chosen by Claude across 8 distinct tools |
| Evidence | 44 items: 9 metrics, 8 log lines, 5 log patterns, 5 documents, 5 past incidents, 3 deployments, 3 alerts, 3 service events, 1 commit, 1 pull request, 1 dependency |

**What Claude concluded.** Top hypothesis at 82%, "likely": checkout-service v2.14.0 reduced the database pool to 10 and the pool is saturated. This is the cause planted in the demo data. It ranked two alternatives below it (a database-side constraint at 20%, an upstream dependency at 5%) and said why each fits less well.

**How it handled uncertainty.**
- It listed evidence *against* its own top hypothesis: the connection metric averaged 12.2 instead of sitting flat at the maximum as the runbook predicts, and the pull request claimed a passing load test.
- It flagged that the pool change is known only from pull-request text marked as sample data, and that the configuration diff was not checked.
- It stated what is missing: the effective pool setting on the running pods, and the database's own connection usage.
- It did **not** propose a rollback, because the previous version was not in its evidence. It proposed finding the rollback target first, and restoring the pool size only after the database team agrees. `rootCauseConfirmed` is false.

**Traceability.** Every evidence item with a record id was looked up in the database: 3 of 3 alerts, 3 of 3 deployments, 3 of 3 service events, 5 of 5 incidents, 8 of 8 log lines, 5 of 5 knowledge chunks, 1 of 1 pull request and 1 of 1 commit exist. (Log patterns, metrics and dependency items are aggregates and carry a composite key rather than a row id.) The report cites 31 of the 44 items, and all citations resolve. The guardrails removed nothing: the model invented no references.

**Governance.** Both recommendations were stored as `PROPOSED` by `ai_agent`, medium risk, one approval required, zero approvals recorded, nothing executed, no deployment created. All 15 tool calls are in the audit log under the AI agent.

## Defect found by the live run

The first investigation attempt gathered evidence correctly (Claude made 12 tool calls), then Anthropic rejected the report request:

> The compiled grammar is too large, which would cause performance issues.

The report schema had many optional and nullable fields, which makes the grammar the provider compiles for structured output too large. Mocked tests cannot catch this because the limit exists only on the real API.

What happened at the time was the designed failure behaviour: the rule-based engine wrote the report from the evidence Claude had gathered, and the investigation was labelled "Rule-based engine · Claude was unavailable" with the reason. Cost of that attempt: $0.007476.

Fix: the schema the model fills in is now flat, with every field required and empty values meaning "not applicable", and is converted to the stored report in code. As a second line of defence, if a provider refuses to compile a schema the request is retried once as plain JSON validated locally. One small live request ($0.000620) confirmed the new schema is accepted before the investigation was run again. Two regression tests cover it.

## Observations and remaining issues

1. **Output tokens are the main cost.** 14,678 output tokens for one investigation is mostly reasoning at `medium` effort. `ANTHROPIC_EFFORT=low` should cut cost and time substantially; whether quality holds needs measuring.
2. **Duration.** About a minute of model time. Acceptable for an investigation, but the interface only shows progress per completed step.
3. **Claude's first code-change query used too narrow a time window** and returned nothing; it recovered with a wider query two rounds later. The tool description could state that merges usually precede the deployment by hours.
4. **It did not find the previous deployment**, because it listed deployments from 08:00 that day and the earlier version was two days old. A tool that returns "the previous successful deployment of this service" would let it propose a concrete rollback.
5. **The evaluation set has now been run once against the model** (see "Live evaluation" below). It exposed flaws in the harness that must be fixed before its scores mean much.
6. **Sonnet and Opus are untested live.** Only Haiku was exercised, as requested.

### What this does and does not show

Holds up:
- **No invented evidence in any run.** The guardrails had no non-existent citation to remove in five investigations.
- **No innocent service was blamed**, including the scenario built to tempt it with a change closer in time.
- **The cause was right in substance in all four scenarios that have one.** The single "top cause" failure is the scorer, not the model: the hypothesis names the v4.2.0 cache-schema change, which is the planted cause, but did not repeat the service name in the text the scorer reads.

Does not hold up, and why the headline number should not be read as model quality:
1. **The scenarios use a fixed clock.** Their data is stamped 1 June 2026, while the prompt tells the model the real current time. To a model, the evidence looks five months stale. That is the likely reason for the low confidence in the first scenario (0.30 against an expected 0.55 or more) and for the "healthy" scenario's top hypothesis being that the tools return out-of-date data. The rule-based engine ignores the clock, so this flaw was invisible until a model ran. This is a defect in the harness.
2. **The action check was written for the rule-based engine.** It expects exactly "rollback" or exactly "no action". A model often proposes a low-risk manual check instead, which is reasonable and is scored as a failure. The run did not save the full reports, so which actions were proposed in the four failing cases is not known.
3. **One run per scenario.** Model output varies between runs; these are single samples.

### Follow-up before evaluating again

- Make the scenario clock relative to now, or pass the scenario's clock to the agent as the current time.
- Score actions by safety (no rollback without an implicated deployment; nothing high-risk) rather than by exact type.
- Save each report to disk during a run so failures can be read afterwards without paying again.
- Then repeat, and compare `ANTHROPIC_EFFORT=low` with `medium`.
